## 2. Structure de clés

Paraglide impose des messages **à plat** (chaque clé = une fonction générée). Options considérées :

- **Préfixe par route** (`transactions_*`, `settings_*`…) : **retenu**. Dans ce repo, les routes coïncident déjà avec les domaines fonctionnels (1 page = 1 domaine métier) : grep trivial, migration page par page naturelle, messages serveur d'une action rangés avec leur page.
- Préfixes transverses en complément : `common_*` (Enregistrer, Annuler, textes internes des composants UI) et `nav_*`.
- Par domaine abstrait (ex. `budgeting_*` couvrant budgets + dashboard) : rejeté, recrée un mapping mental que rien dans le code ne matérialise.
- À plat sans convention : rejeté, ~450 clés sans namespace = collisions et clés introuvables.

Format : `{route}_{contexte}_{sens}`, ex. `transactions_filter_category_label`, `settings_backup_restore_confirm`.

## 3. Setup Paraglide JS

- **Dépendance** : `@inlang/paraglide-js` **v2** uniquement (devDependency ; l'ancien `paraglide-sveltekit` est déprécié, tout est fusionné dans le package unique). Compile-time, type-safe, tree-shakeable, **zéro runtime réseau**, compatible avec la politique de dépendances du projet.
- **Fichiers** : `project.inlang/settings.json` (baseLocale `fr`, locales `["fr","en"]`), `messages/fr.json` + `messages/en.json`, plugin `paraglideVitePlugin` dans `vite.config.ts` (outdir `src/lib/paraglide`, gitignoré).
- **Stratégie de locale** : `['cookie', 'preferredLanguage', 'baseLocale']`, pas de préfixe d'URL (app locale mono-utilisateur, évite de toucher toutes les routes). Sélecteur de langue dans `/settings`, changement = rechargement de page (comportement v2 hors stratégie URL).
- **SSR** : `paraglideMiddleware` dans `hooks.server.ts` (AsyncLocalStorage pour isoler la locale par requête, indispensable, sinon fuite de locale entre requêtes concurrentes) + `%paraglide.lang%` dans `app.html`.
- **Frictions connues** :
  - `npm run check` et vitest exigent que le code généré existe → ajouter la compilation au script `prepare` (comme `svelte-kit sync`) ;
  - en Svelte 5/runes, les messages ne sont pas réactifs au changement de locale sans reload, non-problème avec l'approche cookie + reload ;
  - Docker : le plugin Vite compile au build, vérifier que `messages/` et `project.inlang/` sont copiés dans l'étape build.

## 4. Stratégie de migration

**Page par page, FR comme locale de base** : filet de sécurité clé, la valeur extraite = le texte français actuel, donc zéro diff visuel, et une page non migrée continue d'afficher son français en dur sans rien casser (admin, erreurs, imports inclus).

1. **PR socle** : setup Paraglide + `app.html` lang + hooks + sélecteur dans /settings + extraction des composants partagés (`common_*`, `nav_*`).
2. **PR pilote** : petites pages stables (login, register, force-password-change, +error, admin), valide le pattern à faible coût, y compris les messages de `fail()`.
3. **PR par grosse page** : categories, rules, imports/import, budgets, reports, dashboard (+ refactor insights `rules.ts` en clés + params), transactions, settings. Chaque PR migre la page **et** son `+page.server.ts`.
4. **PR finale** : `Intl` → `getLocale()`, passe grep anti-résidus, puis traduction EN (clé par clé possible : une clé manquante en EN retombe sur le FR).

Le « tout d'un coup » est rejeté : ~450 chaînes sur des pages de 800 lignes = diff inreviewable, et 37 fichiers de specs assertent des chaînes françaises : les échecs doivent se trier page par page.

## 5. Ce qui reste en dur

- **`UNCLASSIFIED_CATEGORY = 'Non catégorisé'`** : valeur **stockée en DB et comparée** partout (pile « à classer », restauration backup). Ne jamais traduire la valeur stockée ; traduire uniquement à l'affichage via un helper. ⚠️ Décision à valider.
- **`DEFAULT_CATEGORIES`** (Alimentation, Transport…) : données utilisateur seedées une fois. Option recommandée : seeder selon la locale au register ; l'existant reste français. ⚠️ Décision à valider.
- Codes techniques : natures (`income`, `spending`…), `bankOperationType`, sources, statuts d'insight (`over_budget`), déjà des codes, seuls leurs **labels d'affichage** passent en clés.
- Chaînes de matching des profils d'import bancaire (`banque_populaire`, `revolut`) : parsing de fichiers source, pas de l'UI.
- Fixtures de tests, logs serveur, variables d'env, `CLAUDE.md`.
- **Cas limite : prompt LLM** (`server/insights/prompt.ts`, en français) : le conseil IA doit-il suivre la locale ? Recommandation : passer la locale dans le prompt, mais ça touche le périmètre sécurité Ollama → security-reviewer sur cette PR-là. ⚠️ Décision à valider.
