The finding

The largest post‑1.0 chantier had no issue

Merchant normalisation was named the largest post‑1.0 chantier a week ago and existed only in a conversation — the same class as the column mapping path, which stayed invisible through four shipped PRs. It was filed as #520 before anything was sorted.

The premise was wrong, and correcting it makes the chantier smaller

It was raised as « 157 rules match the full label, so they cannot fire on CB****PRET A MANGER 44N… ». Measured against the real catalogue and the real matcher, that is not what the code does: matching is substring containment over an accent‑folded label, so a prefix or a suffix costs nothing at all.

The failure is the 41 multi‑token patterns of 141, and only when something touches the separator inside the name. Not the matcher, which is doing the right thing. Not the 100 single‑token patterns, which survive every shape measured.

This correction is now the top of the issue rather than a footnote, because « the rules cannot fire on dirty labels » gets planned as a rewrite of the matcher — and that is not the work.

Noise shape Example Rules broken After normalising
Surrounded by noise CARTE 12/08 CB****SUPER U 44N 0 / 141 —

Separator → hyphen SUPER-U 41 / 41 41 / 41 fire

Separator removed SUPERU 41 / 41 3 / 41 fire
Code inserted mid‑name SUPER 44N U 41 / 41 3 / 41 fire

The right‑hand column is normalizeRecurringLabel, a function this repository already ships and already stores beside a raw label. Three of five broken shapes go to 41 / 41 for free. The two that stay broken are the chantier: token‑level removal of processor references, location codes and card fragments, rather than character folding.

The decision the issue is waiting on

Is the cleaned merchant name an index or a presentation? The additive half is settled and is not the question: RecurringStreamAction.normalizedLabel already stores this exact shape beside a raw label, and replacing the stored label instead would move every deduplication key that exists — buildRowGroupKey joins the folded label into the key and the unique constraint sits on its hash.

What remains decides the release. A cleaned name only the matcher reads is an index: invisible, additive, a 1.x. But the screens keep rendering CB****PRET A MANGER 44N 12/08, and the raw descriptor is the thing a user cannot read. If the cleaned name is what a person should see, it is a presentation, every surface that renders a label is in scope, and the question of which one is the label comes back with it.

The second finding · #521, a precondition of #520

Three functions already fold a label, and they disagree

A chantier about normalising labels, in a tree where three functions already normalise labels differently and nothing says so. Whoever picks up #520 must not add a fourth — which is why this is an issue rather than a comment fix.

Four of five sample inputs get different answers from the three folds. The sharpest fact is not a defect: computeNameKey("CAFÉ") === computeNameKey("cafe") is true while foldLabelForSource("csv", …) says false. The same two strings are one name and two transactions, simultaneously, by design — two spellings of a category mean one category, and two fingerprints that differ at all mean two payments, one of which folding would silently swallow.

Seventh instance · a stated invariant a later change falsified

CLAUDE.md reads « computeNameKey is the only folding in this repo ». True about names, false about labels, and the two words were being used interchangeably. computeNameKey is not a fold at all — it is a hash over normalizeForMatch — and it really is the only folding of a name. Transaction labels are folded twice more, for two other purposes.

The dangerous kind the rule names: a why‑comment, trusted because it justifies, and therefore never re‑read. It lives in an untracked file, which is why the record is an issue.

This is not a request to unify them. Three deliberate foldings is a defensible answer; three foldings nobody can enumerate is not. One divergence does look accidental rather than argued, and is called out for a ruling: foldLabelForSource strips accents only for enablebanking, so a CSV import and a bank sync of the same payment fold differently.

Why Post‑1.0 drifted, and why it was not a discipline failure

Its own description sets the test — « the test is whether a user notices the absence » — and 20 of its 30 were defects and debt, which are not absences. It became the parking bay because it is the only milestone whose name does not commit to a subject, so anything deferred fits it by construction. The timing signal was deliberately not preserved: only the screen‑reader pass stands before 1.0, so not before then said nothing.

Recorded, not promoted

The 1.0 bar has a gap, and naming it beats widening it

Two issues were raised as 1.0 candidates and deliberately not filed there. Criterion 3 reads « no open issue causes a security risk or data loss », and neither causes either — every row lands, nothing is dropped, nothing is exposed. The criterion as written does not admit them and was not bent to fit.

Issue What it does Why the bar misses it
#433 A month/day statement imports on the wrong date, silently, by up to eleven months. No loss and no exposure. Its own body: the one limitation a user cannot detect from the screen.
#485 A multi‑account statement files every row into one account; both balances then wrong. No loss and no boundary crossed — the account is the importing user’s own.

Both write wrong data that looks right. A transaction dated eleven months wrong is worse than one lost — a lost one you notice. The open question, recorded on both issues rather than in a conversation: should the bar gain a fourth trigger, silent data corruption, distinct from data loss? That decision is to be taken before 1.0. Neither issue’s priority changed today; both sit in The import path.
