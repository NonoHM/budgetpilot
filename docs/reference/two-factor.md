# Two-factor authentication: figures and limits

Checked against a running instance, not recalled. For the steps, see
[two-factor authentication](../using/two-factor.md).

## The codes

|                         |                                         |
| ----------------------- | --------------------------------------- |
| Standard                | TOTP, six digits                        |
| Period                  | 30 seconds                              |
| Accepted clock drift    | **one period either side**              |
| Uses per code           | **one**                                 |
| Secret length           | 160 bits, shown as a 32-character key   |
| Issuer shown in the app | `BudgetPilot`, labelled with your email |

The QR code is generated by your own instance and never leaves it.

A code is accepted once, wherever it is typed: signing in, enabling two-factor,
or confirming a change in Settings or Admin. Once a code is accepted, that code,
or an earlier one still inside the drift window, is refused with _This code was
already used. Wait for your app to show a new one._ An earlier code outside the
window is refused like any wrong code. The code typed to enable two-factor
counts as used.
Measured against SQLite, PostgreSQL and MariaDB by
`src/lib/server/auth/totpSingleUse.db-smoke.ts`, not on a running instance.

## Recovery codes

|                    |                                             |
| ------------------ | ------------------------------------------- |
| Issued             | **10**, at the moment two-factor is enabled |
| Format             | `A1B2C-3D4E5`, uppercase hexadecimal        |
| Uses per code      | **one**                                     |
| Shown              | **once**, and never again                   |
| Stored as          | a bcrypt hash, like a password              |
| Regenerating a set | not possible while two-factor is on         |

Measured on a running instance: ten codes issued, all ten accepted in turn,
and a code presented a second time refused with _Invalid code_.

Turning two-factor off deletes every remaining code. Turning it on again
issues a fresh ten.

## What each step verifies

| Step       | Requires                                 |
| ---------- | ---------------------------------------- |
| Enabling   | current password **and** a valid code    |
| Disabling  | current password **and** a valid code    |
| Signing in | password, then a code or a recovery code |

Enabling asks for the password on purpose: without it, an already-open
session would be enough to enrol an attacker's device and read the ten
recovery codes off the screen.

At enrolment, a wrong password and a wrong code read the same: _Incorrect
password or code._ The screen does not say which one failed, so a session left
open on someone else's device does not tell them whether they guessed the
password right.

## Other sessions

Turning two-factor on or off changes how the account signs in. Like a password
change, it ends every other session and every sign-in still in progress.

| When two-factor is turned on or off                       | What happens                                                                |
| --------------------------------------------------------- | --------------------------------------------------------------------------- |
| Every other session of the account                        | **revoked**                                                                 |
| The session that made the change                          | kept, with a new cookie                                                     |
| A sign-in waiting for its code                            | ended: the code is refused and the person is sent back to the password page |
| A sign-in whose password was being checked at that moment | refused with _Invalid credentials_                                          |
| Sessions of other accounts                                | untouched                                                                   |

That sign-in is refused for its timing, not its password: the password was
right, and signing in again works. Without the refusal, a sign-in proven by the
password alone could finish after two-factor was turned on.

Measured against SQLite, PostgreSQL and MariaDB by
`src/lib/server/auth/sessionRotation.db-smoke.ts` and
`src/lib/server/auth/pendingSignIn.db-smoke.ts`
([#949](https://github.com/NonoHM/budgetpilot/issues/949)).

## Rate limiting

Five failed attempts within fifteen minutes, counted per challenge and per
IP address, then _Too many attempts. Try again in a few minutes._

The pending challenge between the two sign-in steps lasts **five minutes**.
After that, the verification page sends you back to sign in with your
password again.

A password change, an admin password reset, turning two-factor off, or
**Log out other sessions** ends a pending challenge at once: a code entered afterwards sends you back to
sign in with your password.

## When the recovery codes run out

Nothing in the app says so.

- **Settings shows no count.** Measured: with two-factor enabled, the word
  _Recovery_ does not appear anywhere on the page, and there is no control
  to issue a new set.
- **The verification page still offers them.** With all ten spent, the page
  continues to read _"Enter the code from your authenticator app, or one of
  your recovery codes."_ and _"Lost your device? Use one of your recovery
  codes instead of the 6-digit code."_

For a user who has spent all ten and lost their phone, that sentence names
the one action that cannot work. Recorded as a known issue rather than
documented as behaviour.

## Recovering a locked-out account

| Route                                | Works?                                                                     |
| ------------------------------------ | -------------------------------------------------------------------------- |
| A recovery code                      | yes, while any remain                                                      |
| Turning it off with a recovery code  | only when the stored secret can't be decrypted, usually after a key change |
| An admin resetting the password      | **no**                                                                     |
| An admin action to disable it        | **does not exist**                                                         |
| Clearing the columns in the database | yes, and the only way with no recovery code left                           |

The password reset was measured rather than assumed: it issues a temporary
password and revokes the account's sessions, and signing in with that
password still redirects to the verification page.

Clearing `totpEnabled` and `totpSecretEncrypted` on the user's row restores
password-only sign-in. Also measured, on a throwaway instance, so the
procedure in the how-to is one that has been run rather than one that ought
to work. Set `totpLastUsedStep` to `NULL` in the same change, so the row reads
as turning two-factor off leaves it: no code accepted since. That third column
was added after the measurement, by #818.

## The encryption key

The TOTP secret is stored encrypted with `TOTP_ENCRYPTION_KEY`
([configuration](../configuration.md)). If that key is changed or lost,
every stored secret becomes undecryptable, for every account that has
two-factor enabled. Back the key up, and keep that copy **apart from the
database backups**: a backup that carries its own key protects the secrets
in it from nobody who gets hold of it
([operations](../operations.md#the-encryption-key)).

What an account with an unreadable secret meets, measured on a running
instance with the key changed after enrolment:

| Where                           | What happens                                                                                                      |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Signing in with a code          | Refused with _Codes from your authenticator app can't be checked for this account any more. Use a recovery code._ |
| Signing in with a recovery code | Works, and spends it                                                                                              |
| Settings                        | The switch stays on, with _Codes can't be checked any more. Turn this off with a recovery code, then on again._   |
| Turning it off                  | Password plus a recovery code, which is spent. Only in this state: a readable setup still asks for a code         |
| Any other confirmation          | Refused until two-factor is set up again: a recovery code is not accepted there                                   |
| Turning it on again over it     | Refused: turn it off first                                                                                        |
| The log                         | `crypt_decrypt_fail` each time a code is checked against it, not when a page only shows it                        |

The unreadable secret is still a second factor. It is never treated as
« no two-factor », so no action falls back to the password alone.
