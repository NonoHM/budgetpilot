NetWorthAccount / NetWorthSnapshot — post-audit

- NetWorthAccount : type (enum checking|savings|investment|debt|real_estate|other), balanceCents, deletedAt (soft delete, unicité (userId, name) sur les actifs seulement, appliquée applicativement dans service.ts).
- NetWorthSnapshot : type gelé à la capture (jamais re-dérivé), capturedAt avec backdating validé (jamais dans le futur), un snapshot par changement de solde OU de type, TOCTOU fermé (read-then-write dans la même transaction).
- Points de contact : server/net-worth/service.ts (CRUD), domain/netWorth.ts (agrégation pure par compte), routes/net-worth/*, domain/netWorthLabels.ts, backup.

2. Options de fusion

Option A — Fusion complète (un seul modèle)

Ajouter type?, balanceCents?, deletedAt à Account, migrer les lignes NetWorthAccount, repntId.
- Migration : lourde — fusion de deux populations avec des contrats d'unicité incompatibles (@@unique(userId, name, source) en DB vs unicité applicative sur actifs seulement côté net worth). Il faut choisir
un contrat et réécrire assertNameAvailable.
- Régressions : le soft delete arrive sur un modèle référencé par Transaction (que devient une transaction d'un compte soft-deleted dans reports/dashboard ?) ; backup change de schéma pour 4 collections d'un
coup ; les buckets implicites ('Compte manuel', 'Compte import CSV') deviennent des compturdes qu'il faut migrer/fusionner.
- Complexité vs objectif : c'est le vrai modèle cible Monarch/YNAB, mais en big-bang ça touche imports + transactions + backup + net-worth simultanément, sur un modèle qui vient d'être durci par audit. Risque
maximal.

Option B — Lien nullable de Account vers NetWorthAccount

Account.netWorthAccountId String? (FK, indexée, non unique : plusieurs buckets techniquesmpte réel — cas typique : le bucket manuel ET le bucket CSV correspondent au même comptecourant).
- Migration : une colonne nullable, zéro mouvement de données, tout l'existant reste valipart).
- Régressions : quasi nulles au départ ; chaque consommateur adopte le lien à son rythme. Backup : un champ optionnel de plus + ordre de remap (netWorthAccounts avant accounts).
- Complexité : deux entités persistent, mais chacune garde ses invariants audités. Le "sorthAccount), pas de duplication.

Option C — NetWorthAccount source de vérité du solde, Account purement transactionnel

Sémantiquement, c'est déjà l'état actuel (le solde n'existe que côté net worth) plus la mtée avec NetWorthAccount comme entité produit primaire. La seule vraie différence avec Best le sens du FK et le vocabulaire UI. B et C convergent vers la même implémentation ; C est la bonne lecture produit de B : l'utilisateur voit des "comptes" (= NetWorthAccount), l'entité Account redevient
un détail interne de rattachement des transactions.

3. Données sensibles / E2EE futur

- Aucune option n'expose de nouveau champ en clair : le serveur lit déjà NetWorthAccount.en clair aujourd'hui. La fusion ne change pas la surface, elle change la colocalisation.
- Option A colocalise soldes et transactions sur le même modèle : pour un E2EE futur, il faudrait chiffrer sélectivement des colonnes d'un modèle central très requêté (filtres serveur sur Transaction.account
compris) — plutôt plus dur.
- Options B/C gardent le patrimoine isolé dans un modèle dédié : un chiffrement "en bloc" de NetWorthAccount/NetWorthSnapshot resterait envisageable sans toucher au moteur de recherche/filtrage des
transactions. Légèrement plus favorable, sans être décisif — décision à part, comme prévu

4. UI/UX

- Le postulat "deux formulaires" est à nuancer : il n'existe qu'un seul formulaire de comôté import, le compte est créé silencieusement. Le flux unifié consiste donc à enrichir le formulaire existant de /net-worth (option "connecté aux transactions" pour les types transactionnels) et à ajouter, dans le flux d'import, un sélecteur de compte de destination (le Combobox partagé) à la
place du bucket implicite.
- Pas de vocabulaire visuel nouveau : c'est de la réorganisation de composants existants (Modal, Select/Combobox, un badge "connecté" dans le style des badges existants, ListCard pour mobile). Pas de
justification pour un passage Claude Design ; le donut/courbe net worth ne changent pas.
- Comptes non transactionnels (real_estate, other, et investment/debt déclaratifs) : ils restent en déclaratif pur naturellement — l'option "connecter aux transactions" n'est simplement pas proposée (ou
repliée, progressive disclosure). Aucune notion d'import forcée.
- À terme, envisager de renommer la page /net-worth en "Comptes" (/accounts) avec la vue patrimoine comme onglet/section — mais c'est une décision produit séparée.

5. Recommandation

Option B/C combinée : FK nullable Account.netWorthAccountId (N buckets techniques → 1 compte patrimoine), avec NetWorthAccount comme entité produit visible et le solde restant 100 % déclaratif dans un premier
temps. C'est la seule option qui donne le modèle mental Monarch/YNAB sans big-bang sur unbackup, et elle laisse la porte ouverte à une absorption complète (option A) plus tard si le lien s'avère systématique.

Découpage suggéré (chaque étape shippable et testable seule) :
1. Schéma : ajout du FK nullable + index, onDelete: SetNull, migration Prisma triviale. Ble Zod + remap (créer les netWorthAccounts avant les accounts à la restore). Aucunchangement de comportement.
2. Liaison à l'import : sélecteur "compte de destination" sur /import (création à la voléet porte le lien. Idem pour ensureManualAccount via un choix sur la saisie manuelle.
3. Surface UI : badge "connecté" sur /net-worth, nom du compte patrimoine dans le détail transaction (à la place de name · source brut), formulaire unifié.
4. (Optionnel, plus tard) : suggestion de solde dérivé des transactions ("solde calculé vabsorption complète.

Risques à surveiller :
- Backup round-trip : l'ordre de recréation et le remap d'ids croisé entre les deux maps (accountIdMap / netWorthAccountIdMap) — bien couvrir le cas FK vers un compte soft-deleted.
- Sémantique du soft delete d'un NetWorthAccount lié : définir explicitement (délier ? gae ?) plutôt que laisser Prisma décider.
- Collision des contrats d'unicité si on migre plus tard vers A — documenter dès l'étape 1 que l'unicité de nom reste applicative côté patrimoine.
- Les buckets legacy ('Compte manuel', 'Compte import CSV') : prévoir un chemin de rattacnnées existantes, sinon l'historique reste orphelin du nouveau modèle.
